## 4. O `ci.yml` do umbrella

```yaml
name: CI
on:
  pull_request:
    branches: [develop]
  push:
    branches: [develop, main]
  workflow_dispatch:

permissions:
  contents: read

concurrency:
  group: ci-${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true

jobs:
  specs:      # cargo xtask check-docs  -> INDEX, links, REQ x backlog, ADR
  tooling:    # cargo fmt/clippy/test --package xtask
  submodules: # cada libs/* e apps/* fixado em tag, não em branch
  arch:       # as 5 regras de 01-arvore-final.md §3
  gate:       # if: always(); soma dos resultados
```

O job `arch` é o único inteiramente novo, e é o que dá sentido à reorganização:

```bash
# 1. decode/encode/output nao dependem de vynamp-* de dominio
cargo tree -p vynamp-decode --prefix none | grep -E '^vynamp-(engine|player|converter|restore)\b' && exit 1
# 2. dsp nao depende de nada do projeto
cargo tree -p vynamp-dsp   --prefix none | grep -E '^vynamp-' && exit 1
# 3. so o engine tem mais de uma lib do projeto
# 4. ninguem depende de apps
# 5. cada lib compila sozinha
for d in libs/*; do cargo build --manifest-path "$d/Cargo.toml" || exit 1; done
```

### Fixture do teste de referência (M7)

O MP3 de referência é provido **dentro do job `test`** do `ci-app.yml`, não por um job
separado:

```yaml
  test:
    runs-on: ubuntu-22.04
    env:
      VYNAMP_MP3_REFERENCE: ${{ github.workspace }}/fixtures/reference.mp3
    steps:
      - uses: actions/checkout@11bd71901bbe5b1630ceea73d27597364c9af683
        with:
          persist-credentials: false
      - run: ./scripts/fetch-fixtures.sh   # baixa e confere sha256 do fixture
      - run: cargo test --all
```

**Por que não um job separado.** `$GITHUB_ENV` e o bloco `env:` de um workflow são
escopados ao **job**, não ao workflow: uma variável exportada no job `fixtures` não
chega ao job `test`. A primeira versão do template tentava exatamente isso e o teste
de referência rodaria sempre ignorado — falha silenciosa, o tipo pior. Um job separado
só funcionaria com `outputs:` e `needs:`, o que é mais máquina para o mesmo resultado.

Sem `actions/cache`: hoje o repo usa **uma única action** (`actions/checkout`, SHA
`11bd719…`). Acrescentar uma segunda exigiria escolher um SHA real e revalidá-lo a cada
atualização — trabalho que não paga nesta fase. O fixture é pequeno e é baixado de novo
a cada run.

O teste de referência preta lê `VYNAMP_MP3_REFERENCE`; se a variável não existir, é
`#[ignore = "VYNAMP_MP3_REFERENCE ausente: ver ci-app.yml job test"]`. Teste pulado
aparece listado no `cargo test` — não some.

## 7. A parte que é código, não script

O `.ps1` aplica as 5 trocas de caminho e a exclusão de diretório (mecânico, reversível,
verificável) e escreve os workflows. **Não** reescreve `delivery()` nem
`github_actions()` por regex: são ~90 linhas de lógica com testes própios em
`validate.rs:587-730`, e um regex que erre ali deixa o gate verde mentindo.

Isso vira **TASK-CI-01** no passo 37:

> **TASK-CI-01** — Rework de `delivery()` e `github_actions()` para a árvore do umbrella
> * Módulo dono: `vynamp` · Modelo: Sonnet · Depende de: passo 34
> * Dado que o umbrella não tem mais `docs/` nem `packaging/`
>   Quando `cargo xtask check-delivery` roda
>   Então ele valida spec, `xtask`, pins de submódulo e regras de arquitetura, e nada de empacotamento
> * Critério: `validate.rs:587-730` (fixtures) reescrito; os 3 testes de workflow passam com o `ci.yml` novo; `check-delivery` verde com os submódulos vazios do passo 31

Até essa TASK fechar, `cargo xtask check-delivery` fica **vermelho por motivo conhecido**
— e o script diz isso em vez de esconder.
